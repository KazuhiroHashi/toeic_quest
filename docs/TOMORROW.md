## ⚠️ 2026-09-19：アップロードが弾かれた。1.0.1 は使い終わっている

Xcode から 1.0.1 (11) を上げたら、2つのエラーで落ちた。

```
90186  Invalid Pre-Release Train.
       The train version '1.0.1' is closed for new build submissions

90062  This bundle is invalid. The value for key CFBundleShortVersionString [1.0.1]
       in the Info.plist file must contain a higher version than that of
       the previously approved version [1.0.1].
```

### 何が起きていたか

**9/16 の提出のとき、番号が2つの場所でずれていた。**

| | 値 |
|---|---|
| App Store Connect のバージョン記録 | **1.0** |
| 中に入れたビルドの `CFBundleShortVersionString` | **1.0.1** |

この組み合わせのまま承認されたので、**Apple から見ると 1.0.1 は消化済みの番号**。
一方 App Store Connect には「1.0.1 提出準備中」という記録が残っていて、
こちらは**永久に埋められない**。1.0.1 のビルドはもう受け付けられないため。

`version.json` の `name` を 1.0.1 のままにしていたのが直接の原因。
ビルド番号（`code`）だけ上げれば済むと思っていたが、**バージョン文字列のほうが
塞がっていた。**

### どう直したか

`version.json` を `1.0.2` にした。ビルド番号は 11 のまま
（アップロードが失敗しているので、11 はまだ Apple に登録されていない）。

```json
{ "code": 11, "name": "1.0.2" }
```

**App Store Connect 側も「バージョン」欄を 1.0.2 に直す必要がある。**
記録を作り直さなくてよい。あの欄は提出準備中なら編集できる。

### 次から踏まないために

**App Store Connect のバージョン記録の番号と、`version.json` の `name` を必ず一致させる。**
食い違ったまま承認されると、片方の番号が使えなくなる。

提出の前に、この2つを並べて見ること。

```
App Store Connect の「バージョン」欄   ←→   version.json の name
```

### versionCode のこと

Play は**同じ versionCode のファイルを二度は受け付けません**。出し直すたびに
1つずつ上げる必要があります。

ところが `npx cap add android` で作り直すと、この番号は**必ず 1 に戻ります**。
手で直していると、作り直すたびに戻り、気づかずアップロードして弾かれる。

そこで番号は `version.json` に置き、`npm run cap:sync` が毎回そこから
書き戻すようにした（`tools/apply_version.js`）。**android/ を何度作り直しても
番号は保たれます。**

```
npm run bump        version.json の code を 1つ上げる（出し直す前に一度だけ）
npm run cap:sync    android/ に書き込む（自動で呼ばれる）
```

> 「このバージョンコードは既に使用されています」と Play に言われたら、
> `npm run bump` を忘れています。上げて作り直せば通ります。

> **`npm run cap:sync` を `npx cap sync` で代用しないこと。**
> AdMob のアプリIDが AndroidManifest.xml に入らず、**広告が一切出なくなります。**

## F. 製品版リリース → 審査に送信

審査は **数日〜7日**。新規アプリの初回は長めです。

### ⚠️ リリースノートは利用者に見える

紛らわしいので整理しておく。

| | 見えるか |
|---|---|
| リリース名（`2 (1.0)` など） | **見えない。** Console の一覧で見分けるためだけの名前 |
| リリースノート | **見える。** ストアの「最新情報」欄に出る |

**初回は空欄でよい**（2026-09-13 本人の判断）。リリースノートは必須ではなく、
書かなければストアに「最新情報」の欄そのものが出ない。

初回に書く意味は薄い。アプリの説明は掲載情報の説明文がすでに担っていて、
そこに「単語帳を開くより、冒険しよう。」がある。同じ場所で二度説明しない。

**書くとしても「修正しました」とは書かないこと。** まだ誰も前の版を使って
いないので意味が通らないうえ、「不具合があった」と伝えることになる
（利用者には不具合を伝えない方針・2026-09-10）。

2本目以降も同じ。「〜を修正しました」ではなく「〜を改善しました」
「〜が遊びやすくなりました」。同じ内容でも受け取られ方が違う。

> 内部テストのリリースノートは、読むのが自分だけなので何を書いてもよい。
> 実際 `2 (1.0)` には「効果音と広告まわりの修正」と書いてある。

### ~~BGM のループの継ぎ目~~ → 出荷分は済（2026-09-13）

**何のことか。** Suno は曲の最後を必ずフェードアウトさせる。ところが
アプリは `<audio loop>` で鳴らすので、**音が消えたあと、いきなり頭から
鳴り直す**。「スーッと消えて、ドン」と聞こえる、あれのこと。
`tools/loop_bgm.js` がフェードを切り落として、末尾を曲の頭につなぎ直す。

**以前ここに書いてあった10曲の名前は間違っていました。**
`arena1〜4, boss, king2〜4, lastboss, midboss` と書いてありましたが、
測ったらこれらは**すでに処理済み**でした。実際に残っていたのは別の曲です。
数だけ合っていて、中身が入れ替わっていた。

いまの状態は、いつでもこれで確かめられます（何も書き換えません）：

```bash
node tools/loop_bgm.js assets/bgm/*.mp3 --check
```

**出荷ビルドに入る曲は、全部かたづきました。**

| 曲 | 直した | なぜ |
|---|---|---|
| `title` | ✅ 58dB → 3dB | タイトル画面。**全員が必ず聞く**。4分で一周する |
| `ending` | ✅ 73dB → 6dB | エンディング。6dBは曲そのものの静かな終わり方（実測で確認） |
| `gameover` | ✅ 47dB → 0.5dB | 全滅の曲 |

**★が残っている曲は、直さなくてよい。** 理由：

- `field` `town` `dungeon` `battle_dungeon` … 制作中のストーリーモード専用。
  `tools/build_www.js` の `SKIP_BGM` で**出荷ビルドに入っていない**
- `battle` `battle2` … 入ってはいるが、**鳴る場面が無い**。戦闘の曲は
  11曲すべてが `bgm:` で名指しされていて（arena1〜4/king1〜4/boss/midboss/
  lastboss）、この2曲は「名指しが無かったとき」の保険。出番が来ない
- `victory` … 6秒のファンファーレ。**ループしない**ので、
  フェードアウトが正しい。効果音として鳴らしている（`pbattle.js`）

> `battle` と `battle2` を同梱から外せば **5.6MB 減らせます**が、
> 保険を外すことになるので、公開を急ぐいまは触っていません。
